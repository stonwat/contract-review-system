### 一、架构演进思路

当前 contract-compare Skill 的局限：

- 数据存 CSV，无法并发、无法查询、无法做统计聚合
- 全靠 Agent 单线程驱动，没有持久化任务队列
- 没有前端，审查人员只能通过对话交互

演进方向：本地 Agent 负责感知（OCR + LLM提取），服务器负责存储与计算（API + DB + 报表），前端负责呈现

```
┌─────────────────────────────────────────────────────────────────────┐
│                         前端 Vue 3 + Element Plus                    │
│  合同管理 │ 比对审查 │ 验收管理 │ 风险看板 │ 报表中心 │ 项目总览      │
└───────────────────────────────────────────┬─────────────────────────┘
                                            │ HTTPS
┌───────────────────────────────────────────▼─────────────────────────┐
│                   后端 FastAPI (Python 3.11+)                       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ │
│  │ 文件管理   │ │ 合同CRUD  │ │ 比对引擎   │ │ 报表生成   │ │ 风险评估   │ │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘ └──────────┘ │
│  ┌──────────┐ ┌──────────┐ ┌──────────────────────────────────────┐│
│  │ 用户认证   │ │ 项目管理   │ │   LLM 比对调度（调用大模型做语义比对）   ││

  │PostgreSQL│   │ MinIO  │       │   Redis   │
```

### 二、核心设计理念

| 原则 | 说明 |
|:---|:---|
| Agent 做感知，Server 做存储 | OCR 和 LLM 提取在本地 Agent 完成，结果通过 API 推送到服务端数据库 |
| API-first | 所有操作都通过 REST API，Agent 和前端都是 API 的消费者 |
| 人工确认环节不省略 | 提取结果标注 `verified=false`，审查人员在 UI 确认后才参与比对 |
| 断点续跑 | 每个阶段记录状态，中断后可从上次位置继续 |
| 前后项判定可回溯 | 判定依据（文件名信号/签约方比对/人工指定）记录在案 |

### 三、数据库表设计

> **核心设计原则**：整个系统以**合同编号（contract_no）**为唯一项目标识。同一个工程项目的前项和后项合同共享同一个合同编号。Agent 通过匹配合同编号自动完成前后项配对。所有业务表通过 `contract_no` 关联，无需额外项目编码字段。项目级信息（地市、负责人、项目名称）统一放在 `projects` 表，其他表不再重复。

#### 3.1 项目表 `projects`

合同编号即项目标识。Agent 在处理首份合同时，若 `contract_no` 不存在则自动创建项目记录。

```sql
CREATE TABLE projects (
    contract_no       VARCHAR(100) PRIMARY KEY,  -- 合同编号 = 项目标识
    project_name      VARCHAR(200),
    city              VARCHAR(20),               -- 地市
    responsible_person VARCHAR(50),              -- 负责人
    status            VARCHAR(20) DEFAULT '待审查', -- 待审查/审查中/已完成
    risk_level        VARCHAR(10),               -- 高/中/低
    created_at        TIMESTAMPTZ DEFAULT now(),
    updated_at        TIMESTAMPTZ DEFAULT now()
);
```

#### 3.2 合同表 `contracts`

通过 `contract_no` 关联到项目。项目级信息（city、project_name、responsible_person）已统一在 `projects` 表管理，`contracts` 不再重复存储。Agent 自动匹配同一 `contract_no` 下的两笔记录（前项 + 后项）完成配对。

```sql
CREATE TABLE contracts (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    contract_no       VARCHAR(100) REFERENCES projects(contract_no),
    contract_type     VARCHAR(10) NOT NULL,       -- 前项/后项
    type_judge_basis  VARCHAR(200),               -- 判定依据

    -- 签约方
    party_a           VARCHAR(200),               -- 甲方
    party_b           VARCHAR(200),               -- 乙方
    our_role          VARCHAR(10),                -- 我方角色: 甲方/乙方

    -- 合同信息
    signing_date      DATE,
    contract_period   VARCHAR(100),               -- 工期描述

    -- 金额
    total_amount      DECIMAL(14,2),              -- 合同总金额(元)
    amount_uppercase  VARCHAR(100),               -- 大写金额(校验用)
    tax_rate          DECIMAL(5,4),               -- 税率

    -- 关键条款
    payment_terms     TEXT,                       -- 付款条款
    delivery_terms    TEXT,                       -- 交付条款
    acceptance_terms  TEXT,                       -- 验收条款
    breach_terms      TEXT,                       -- 违约责任
    warranty_terms    TEXT,                       -- 质保条款
    ip_terms          TEXT,                       -- 知识产权条款
    other_key_terms   TEXT,                       -- 其他关键条款

    -- 文件溯源
    source_file_id    UUID,                       -- 关联存储的原始文件
    source_file_name  VARCHAR(300),
    source_file_hash  VARCHAR(64),                -- SHA256，防重复上传
    ocr_raw_text      TEXT,                       -- OCR 原始识别文本
    ocr_engine        VARCHAR(20),
    llm_model         VARCHAR(50),

    -- 状态
    verified          BOOLEAN DEFAULT false,       -- 是否人工确认
    verified_by       VARCHAR(50),
    verified_at       TIMESTAMPTZ,
    extracted_at      TIMESTAMPTZ,
    created_at        TIMESTAMPTZ DEFAULT now(),
    updated_at        TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_contracts_no ON contracts(contract_no);
CREATE INDEX idx_contracts_type ON contracts(contract_no, contract_type);
```

### 五、Agent 端工作流（本地执行）

这是"通过本地 Agent 的 OCR 来识别合同"的核心流程。Agent 通过提取合同编号自动判断哪些合同属于同一项目的前后项：

```
用户指定文件/目录
       │
       ▼
  ┌────────────┐
  │ 文件类型判断 │
  └─────┬──────┘
        │
  ┌─────▼─────────────────────────────────────────────────┐
  │ PDF扫描件/图片                  PDF有文本层 / docx / xls │
  │         │                                    │        │
  │  ┌──────▼───────┐                      直接提取文本      │
  │  │  PaddleOCR   │                        │             │
  │  └──────┬───────┘                        │             │
  │         └───────────┬────────────────────┘             │
  └─────────────────────│──────────────────────────────────┘
                        │
                        ▼
  ┌─────────────────────────┐
  │  LLM 结构化提取          │  ← 按合同字段模板抽取
  └──────────┬──────────────┘
             │
             ▼
  ┌─────────────────────────┐
  │  前后项判定              │  ← 合同编号匹配 → 文件名信号 → 签约方比对 → 人工确认
  └──────────┬──────────────┘
             │
             ▼
  ┌─────────────────────────┐
  │  POST /contracts        │  → 推送到服务端 API
  └─────────────────────────┘
```

Agent 调用示例（伪代码）：

```python
# 1. OCR
ocr_text = paddleocr.recognize(image_path)

# 2. LLM 提取
extracted = llm.extract(ocr_text, schema=CONTRACT_SCHEMA)

# 3. 前后项判定
# 优先级: 合同编号匹配 → 文件名信号 → 签约方比对
contract_type = judge_front_back(extracted, filename)

# 4. 推送到服务端
requests.post("https://server/api/v1/contracts", json={
    "contract_no": extracted.contract_no,
    "contract_type": contract_type,
    "party_a": extracted.party_a,
    "party_b": extracted.party_b,
    "total_amount": extracted.total_amount,
    "ocr_raw_text": ocr_text,
    "source_file_hash": file_hash,
    # ... 其他字段
})
```

### 六、比对引擎设计（服务端）

比对引擎是服务端的核心，分两层：

**第一层：数值比对（纯计算，不调LLM）**

- 金额差异 = 前项 - 后项
- 毛利率 = (前项 - 后项) / 前项
- 分项数量/单价/金额差异
- 风险等级判定（利润倒挂、超量分包、单价倒挂）

**第二层：语义比对（调 LLM）**

- 付款条款一致性 → 需要理解"验收后30日内付款" vs "验收后60日内付款"
- 交付条款一致性
- 验收条款一致性
- 验收内容一致性

语义比对的 Prompt 模板：

```
你是合同审查专家。请比对以下两份合同的{条款类型}条款，判断是否实质一致。
若不一致，具体描述差异。

前项合同{条款类型}条款：
{front_terms}

后项合同{条款类型}条款：
{back_terms}

输出JSON：
{ "match": "一致/不一致", "diff_detail": "具体差异描述" }
```

### 七、报表生成逻辑（对应四个报表）

| 报表 | 汇总 | 明细 | 数据源 |
|:---|:---|:---|:---|
| 合同内容一致性 | 各地市一致数/总数/一致率 | 每对合同的逐项匹配结果 | comparisons |
| 验收报告一致性 | 各地市一致数/总数/一致率 | 每对验收的比对结果 | acceptance_reports |
| 低毛利项目 | 毛利率<3% 的数量 | 项目清单+毛利率+金额 | comparisons (margin_rate < 0.03) |
| 高风险项目 | 同时满足三项的数量 | 完整项目信息 | 三表联查 |

高风险判定 SQL：

```sql
SELECT c.contract_no, p.city, c.front_amount, c.back_amount,
       c.margin_rate, c.payment_match, c.acceptance_match
FROM comparisons c
JOIN projects p ON p.contract_no = c.contract_no
JOIN acceptance_reports ar ON ar.contract_no = c.contract_no
WHERE c.margin_rate < 0.03
  AND (c.payment_match = '不一致' OR c.delivery_match = '不一致'
       OR c.acceptance_match = '不一致' OR c.other_match = '不一致')
  AND ar.comparison_result = '不一致'
```

### 八、技术选型

| 层 | 技术 | 理由 |
|:---|:---|:---|
| 后端框架 | **FastAPI (Python 3.11+)** | 异步、自带 OpenAPI 文档、与现有 Python 脚本兼容 |
| ORM | SQLAlchemy 2.0 | 类型安全、异步支持 |
| 数据库 | **PostgreSQL 16** | JSONB、DECIMAL 精度、全文搜索、CTE 递归查询 |
| 文件存储 | MinIO | S3 兼容、可本地部署、后续上云无缝迁移 |
| 任务队列 | Redis + arq | 轻量级异步任务，OCR/LLM 耗时操作走队列 |
| 前端框架 | **Vue 3 + TypeScript** | 组合式 API、类型安全 |
| UI 组件库 | **Element Plus** | 表格/表单/弹窗开箱即用，适合管理后台 |
| 样式 | TailwindCSS（辅助） | 仅用于间距、布局微调，不做主样式方案 |
| 状态管理 | Pinia | Vue 3 官方推荐 |
| HTTP 客户端 | Axios | 请求拦截、响应拦截、Token 管理 |
| OCR | PaddleOCR（Agent 本地） | 已有项目经验 |

### 九、认证与权限设计

#### 9.1 设计原则

Web 端是管理控制台，区别于 Agent 端认证：

| 端 | 认证方式 | 用户 |
|:---|:---|:---|
| **Web 前端** | JWT 登录（普通账号密码） | 系统管理员/审查人员 |
| **Agent 客户端** | API Key（请求头 `X-API-Key`） | 自动化脚本，由 Agent 配置管理 |

Web 端只需简单的管理员账号体系，不涉及复杂的用户注册和角色管理。Agent 端有自己的认证机制，不在本项目范围内。

#### 9.2 Web 端认证

- 登录接口 `/api/v1/auth/login` 验证账号密码，返回 JWT token（24h 过期）
- 前端 Axios 拦截器自动附加 `Authorization: Bearer <token>`
- 后端通过 `Depends(get_current_admin)` 校验

#### 9.3 管理员表 `admins`

```sql
CREATE TABLE admins (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username      VARCHAR(50) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,       -- bcrypt 哈希
    display_name  VARCHAR(100),
    is_active     BOOLEAN DEFAULT true,
    created_at    TIMESTAMPTZ DEFAULT now()
);
```

#### 9.4 审计日志

所有写操作（create / update / verify / delete / compare）自动记录到 `audit_log` 表，便于追溯操作记录。

### 十一、API 规范

#### 11.1 统一响应格式

所有接口统一返回格式，前端根据 `code` 判断业务结果：

```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

| code | 含义 |
|:---|:---|
| 0 | 成功 |
| 4000 | 请求参数错误 |
| 4001 | 未认证（Token 缺失/过期）|
| 4003 | 无权限 |
| 4040 | 资源不存在 |
| 5000 | 服务器内部错误 |

#### 11.2 分页规范

列表接口统一使用：

```json
// 请求参数
{ "page": 1, "page_size": 20 }

// 响应数据
{
  "code": 0,
  "data": {
    "items": [...],
    "total": 100,
    "page": 1,
    "page_size": 20
  }
}
```

### 十五、非功能性需求

#### 15.1 安全性

- 密码使用 bcrypt 哈希存储
- JWT Token 有效期 24 小时
- 文件上传限制类型（仅 pdf/docx/xls/xlsx/jpg/png），校验 MIME type + 文件头魔数
- 文件大小限制（单文件 50MB）
- 所有 SQL 通过 ORM 参数化查询，防注入
- .env 文件不提交 Git

#### 15.2 性能

- 数据库关键字段建立索引（contract_no、contract_type 等已有索引设计）
- 列表接口必须分页，不允许无 limit 的全量查询
- 大字段（ocr_raw_text）默认不返回，仅详情接口按需查询
- LLM 调用异步执行，不阻塞 API 响应
- 报表查询使用物化索引或汇总缓存（Redis），大数据量不实时计算

#### 15.3 可维护性

- 数据库变更使用 Alembic 迁移脚本，可回滚
- API 自动生成 OpenAPI 文档（FastAPI 内置）
- 操作审计日志可追溯
- Docker 化部署，环境变量配置，不硬编码

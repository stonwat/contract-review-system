### 二、核心设计理念

| 原则 | 说明 |
|:---|:---|
| Agent 做感知与分析，Server 做存储 | OCR、LLM 提取、LLM 对比分析在本地 Agent 完成，结果通过 API 推送到服务端数据库 |
| API-first | 所有操作都通过 REST API，Agent 和前端都是 API 的消费者 |
| 人工确认环节不省略 | 提取结果与 LLM 分析结果均标注 `verified=false`，审查人员在 UI 确认后才生效 |
| 材料完整性驱动 | `projects` 表 4 个布尔标记跟踪材料齐全度，全齐后具备 LLM 分析条件 |
| 分析按需触发 | 风险分析由用户在 Agent 对话中明确指令触发，不自动执行 |
| 前后项判定可回溯 | 判定依据（文件名信号/签约方比对/人工指定）记录在 `type_judge_basis` 字段 |

### 三、数据库表设计

> **核心设计原则**：整个系统以**合同编号（contract_no）**为唯一项目标识。同一个工程项目的前项和后项合同共享同一个合同编号。所有业务表通过 `contract_no` 关联，无需额外项目编码字段。项目级信息（地市、负责人、项目名称、材料完整性标记）统一放在 `projects` 表，其他表不再重复。完整字段说明详见 `05.数据库设计文档.md`。

#### 3.1 项目表 `projects`

```sql
CREATE TABLE projects (
    contract_no          VARCHAR(100) PRIMARY KEY,   -- 合同编号 = 项目标识
    project_name         VARCHAR(200),
    city                 VARCHAR(20),                -- 地市
    responsible_person   VARCHAR(50),                -- 负责人
    -- 材料完整性标记
    has_front_contract   BOOLEAN DEFAULT false,
    has_back_contract    BOOLEAN DEFAULT false,
    has_front_acceptance BOOLEAN DEFAULT false,
    has_back_acceptance  BOOLEAN DEFAULT false,
    -- LLM 分析状态
    llm_analyzed         BOOLEAN DEFAULT false,       -- 四布尔全 true 时可分析
    project_risk         VARCHAR(10),                 -- 低风险/高风险（LLM 推送）
    -- 人工审查
    audit_status         VARCHAR(20) DEFAULT '待审查',-- 待审查/已完成
    audited_by           VARCHAR(50),
    audited_at           TIMESTAMPTZ,
    created_at           TIMESTAMPTZ DEFAULT now(),
    updated_at           TIMESTAMPTZ DEFAULT now()
);
```

### 五、Agent 端工作流（本地执行）

Agent 通过对话窗口接收用户提交的合同/验收文件，并在用户指令下执行风险分析。完整流程详见 `08.工作流程描述.md`，此处为概要：

```
用户提交文件
       │
       ▼
  读取分析文档内容
       │
       ▼
  校验/重命名（项目名称-合同编号-上传人员.扩展名）
       │
       ▼
  判断文档类型（合同 / 验收报告 / 询问用户）
       │
       ▼
  上传 MinIO 归档
       │
       ▼
  查重（contracts/check 或 acceptance/check）
       │
       ▼
  LLM 结构化提取 → 推送后端
       │
       ▼
  后端自动维护 projects.has_* 标记
       │
       ▼
  （用户指令：进行风险分析）
       │
       ▼
  检查全部项目：四布尔齐全且 llm_analyzed=false
       │
       ▼
  LLM 合同对比分析 → 写入 contract_analysis
  LLM 验收对比分析 → 写入 acceptance_report_analysis
       │
       ▼
  LLM 综合判定 → 回写 projects.project_risk + llm_analyzed=true
```

### 六、LLM 分析引擎设计

分析引擎由本地 Agent 驱动，分三个步骤（Prompt 模板详见 `08.工作流程描述.md` 附录）：

**步骤一：合同对比分析**
- 输入：同 contract_no 的前项、后项合同 JSON
- 产出：毛利率 `rate`、等级 `rate_level`、条款一致性 `similarity`、分析文本 `analysis`
- 写入 `contract_analysis`（UPSERT）

**步骤二：验收报告对比分析**
- 输入：同 contract_no 的前项、后项验收报告 JSON
- 产出：内容一致性 `similarity`、分析文本 `analysis`
- 写入 `acceptance_report_analysis`（UPSERT）

**步骤三：综合风险判定**

| 条件 | 风险等级 |
|:---|:---|
| 利润倒挂（rate < 0） | 高风险 |
| 低毛利（0 ≤ rate < 0.05） | 高风险 |
| 任一 similarity 为"完全不一致" | 高风险 |
| 以上条件均不满足 | 低风险 |

回写 `projects.project_risk` + `llm_analyzed=true`。

### 七、报表生成逻辑（对应四个报表）

| 报表 | 汇总 | 明细 | 数据源 |
|:---|:---|:---|:---|
| 合同内容一致性 | 各地市各一致性档位数量 | 每个项目的一致性 + 分析文本 | contract_analysis |
| 验收报告一致性 | 各地市各一致性档位数量 | 每个项目的一致性 + 分析文本 | acceptance_report_analysis |
| 低毛利项目 | 低毛利/利润倒挂数量 | 项目清单+毛利率+金额 | contract_analysis (rate_level IN 低毛利/利润倒挂) |
| 高风险项目 | 高风险数量 | 完整项目信息 | projects (project_risk='高风险') |

高风险项目查询 SQL：

```sql
SELECT p.contract_no, p.city, p.project_risk,
       ca.rate, ca.rate_level, ca.similarity AS contract_similarity,
       ara.similarity AS acceptance_similarity
FROM projects p
LEFT JOIN contract_analysis ca ON ca.contract_no = p.contract_no
LEFT JOIN acceptance_report_analysis ara ON ara.contract_no = p.contract_no
WHERE p.project_risk = '高风险'
```

### 九、认证与权限设计

#### 9.1 双通道认证架构

| 端 | 认证方式 | 身份对象 | 用户 |
|:---|:---|:---|:---|
| **Web 前端** | JWT Bearer Token（`Authorization` 头） | `AdminIdentity`（含 role + city） | 超级管理员 / 省市管理员 / 只读用户 |
| **Agent 客户端** | API Key（`X-API-Key` 头） | `None`（仅校验，无身份） | 自动化脚本 |

#### 9.2 JWT Payload 扩展

```
现有:  { "sub": "<admin_uuid>", "exp": <timestamp> }
改为:  { "sub": "<admin_uuid>", "role": "<role>", "city": "<city|null>", "exp": <timestamp> }
```

- `role`：`super_admin` / `city_admin` / `viewer`
- `city`：`city_admin` 的绑定地市，`super_admin` 和 `viewer` 为 `null`
- **无状态鉴权**：大部分权限判定直接从 token 读取 role 和 city，无需每次查库
- 仍保留登录时查库确认 `is_active`；账号禁用后，下次 token 过期重新登录时生效

#### 9.3 鉴权依赖改造

```python
class AdminIdentity:
    """从 JWT 解析的轻量身份对象，不查库。"""
    id: UUID
    username: str
    role: str        # super_admin / city_admin / viewer
    city: str | None # 绑定地市
```

#### 9.4 权限校验函数

```python
async def require_write_access(identity: AdminIdentity, project_city: str | None):
    """写入操作权限：super_admin 或本市的 city_admin"""
    if identity.role == 'super_admin':
        return
    if identity.role == 'city_admin' and identity.city == project_city:
        return
    raise HTTPException(403, "无权操作该地市的项目")

async def require_export(identity: AdminIdentity):
    """导出权限：super_admin 或 city_admin"""
    if identity.role in ('super_admin', 'city_admin'):
        return
    raise HTTPException(403, "只读用户无导出权限")

async def require_super_admin(identity: AdminIdentity):
    """仅超级管理员"""
    if identity.role == 'super_admin':
        return
    raise HTTPException(403, "仅超级管理员可执行此操作")
```

#### 9.5 数据隔离规则

`city_admin` 请求读取接口时，**不强制过滤**（可浏览所有地市），但写入操作需校验 `projects.city == identity.city`。`super_admin` 无限制。`viewer` 只读无写入。

### 十五、非功能性需求

#### 15.1 安全性

- 密码使用 bcrypt 哈希存储
- JWT Token 有效期 24 小时
- 文件上传限制类型（仅 pdf/docx/xls/xlsx/jpg/png），校验 MIME type + 文件头魔数
- 文件大小限制（单文件 50MB）
- 所有 SQL 通过 ORM 参数化查询，防注入
- .env 文件不提交 Git

- 数据库关键字段建立索引（contract_no、各 analysis 表 contract_no 索引见第三节）
- 列表接口必须分页，不允许无 limit 的全量查询
- LLM 调用异步执行，不阻塞 API 响应
- 报表查询使用汇总缓存（Redis），大数据量不实时计算

- 表结构由 ORM `Base.metadata.create_all` 创建，暂不引入 Alembic 迁移
- API 自动生成 OpenAPI 文档（FastAPI 内置）

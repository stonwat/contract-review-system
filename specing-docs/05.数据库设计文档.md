### 一、设计原则

1. **合同编号即项目标识** — `contract_no` 是项目的唯一标识，前项和后项合同共享同一个 `contract_no`
2. **项目级信息统一管理** — 地市、项目名称、材料完整性标记只存在 `projects` 表，合同金额从 `contracts` 表读取，避免冗余
3. **材料完整性布尔标记** — `projects` 表通过 4 个布尔字段（`has_front_contract`、`has_back_contract`、`has_front_acceptance`、`has_back_acceptance`）跟踪项目材料齐全度，四项全为 `true` 时具备 LLM 分析条件
4. **LLM 分析结果独立存储** — 毛利率、一致性分析等 LLM 产出结果存入 `contract_analysis` 和 `acceptance_report_analysis` 表，与原始业务数据分离
5. **分析覆盖式更新** — 每个项目在两个分析表中各只有一条记录，重新分析时 UPDATE 覆盖旧结果，不追加历史
6. **分析结果可人工确认** — 分析表与合同/验收报告一样具备 `verified` 机制，LLM 结果需人工确认后才生效
7. **项目风险聚合判定** — `projects.project_risk` 由 LLM 综合两个分析表的结果推送，非人工填写
8. **风险分析按需触发** — 四个布尔字段全为 `true` 时项目**具备可分析条件**，但 LLM 分析由用户在 Agent 对话中**明确指令触发**，不自动执行
9. **UUID 主键** — 除 `projects` 以 `contract_no` 为 PK 外，其余业务表使用 UUID 作为主键，避免自增 ID 暴露数据量
10. **时间戳标准化** — 统一使用 `TIMESTAMPTZ` 类型，统一字段名 `created_at` / `updated_at`
11. **精简溯源** — 原始文件存 MinIO，不落库；去除 OCR 文本/引擎等中间数据，保留文件名用于展示
12. **单一关联路径** — 所有业务表只通过 `contract_no` 关联到 `projects`，不建立跨表直接 FK，避免冗余关联链
13. **派生状态应用层维护** — `projects.has_*` 四个布尔标记是 `contracts`/`acceptance_reports` 子表数据的派生状态，由应用层在插入/删除时维护一致性，数据库不做触发器兜底（当前阶段成本权衡）
14. **审查人字段为快照** — `verified_by`/`audited_by` 存用户名快照而非 `admins.id` 外键，即使账号改名或删除，历史审查记录仍可读
15. **枚举值数据库层约束** — 所有枚举字段（`project_risk`/`audit_status`/`rate_level`/`similarity`/`contract_type`/`acceptance_type`/`acceptance_result`）加 CHECK 约束，防止 LLM 或脏数据写入非法值
16. **1:1 关系数据库层保障** — 两个 analysis 表的 `contract_no` 加 UNIQUE 约束，让"每个项目一条记录"在数据库层成立，UPSERT 的 `ON CONFLICT` 有明确冲突列

### 三、表结构

#### 3.1 `projects` — 项目表

合同编号即项目标识。Agent 在处理首份合同时，若 `contract_no` 不存在则自动创建项目记录。**前后项合同共享同一项目记录**，通过 4 个布尔字段跟踪材料完整性，四项齐全后具备 LLM 分析条件（由用户指令触发分析）。

| 字段                   | 类型          | 约束             | 说明                                                       |
| :--------------------- | :------------ | :--------------- | :--------------------------------------------------------- |
| contract_no            | VARCHAR(100)  | PK               | 合同编号，同时也是项目唯一标识                             |
| project_name           | VARCHAR(200)  |                  | 项目名称                                                   |
| city                   | VARCHAR(20)   |                  | 地市（鹤岗/伊春/齐齐哈尔/哈尔滨）                          |
| has_front_contract     | BOOLEAN       | DEFAULT false    | 是否存在前项合同                                           |
| has_back_contract      | BOOLEAN       | DEFAULT false    | 是否存在后项合同                                           |
| has_front_acceptance   | BOOLEAN       | DEFAULT false    | 是否存在前项验收报告                                       |
| has_back_acceptance    | BOOLEAN       | DEFAULT false    | 是否存在后项验收报告                                       |
| llm_analyzed           | BOOLEAN       | DEFAULT false    | 是否经过 LLM 分析（四个布尔全为 true 时可分析）            |
| project_risk           | VARCHAR(10)   | CHECK IN (低风险,高风险) | 项目风险：低风险 / 高风险（LLM 分析后推送）        |
| responsible_person     | VARCHAR(50)   |                  | 项目负责人                                                 |
| audit_status           | VARCHAR(20)   | DEFAULT '待审查', CHECK IN (待审查,已完成) | 审查状态：待审查 / 已完成                  |
| audited_by             | VARCHAR(50)   |                  | 审查人（用户名快照，非外键）                               |
| audited_at             | TIMESTAMPTZ   |                  | 审查时间                                                   |
| created_at             | TIMESTAMPTZ   | DEFAULT now()    |                                                            |
| updated_at             | TIMESTAMPTZ   | DEFAULT now()    |                                                            |

**约束**：

```sql
ALTER TABLE projects ADD CONSTRAINT uq_projects_contract_no UNIQUE (contract_no);  -- 即 PK
ALTER TABLE projects ADD CONSTRAINT ck_projects_project_risk CHECK (project_risk IN ('低风险', '高风险'));
ALTER TABLE projects ADD CONSTRAINT ck_projects_audit_status CHECK (audit_status IN ('待审查', '已完成'));
```

**字段迁移映射**（相对 V1/V2）：

| 旧字段（已废弃） | 新字段 | 说明 |
| :--- | :--- | :--- |
| `status` | `audit_status` | 审查状态字段更名，取值不变（待审查/已完成） |
| `risk_level` | `project_risk` | 风险字段更名，取值由"高/中/低"改为"低风险/高风险"，且改为 LLM 推送 |
| `gross_margin_rate` | `contract_analysis.rate` | 毛利率数值移至合同分析表 |
| `gross_margin_level` | `contract_analysis.rate_level` | 毛利率等级移至合同分析表 |

**说明**：

- `has_front_contract` / `has_back_contract` / `has_front_acceptance` / `has_back_acceptance`：在对应合同/验收报告插入时自动置为 `true`；删除时回置为 `false`
- `llm_analyzed`：四个布尔字段全为 `true` 时项目**具备可分析条件**；用户在 Agent 对话中下达分析指令后执行 LLM 分析，完成后置为 `true`。重新分析时可重置为 `false` 再次触发。
- `project_risk`：LLM 综合 `contract_analysis` 和 `acceptance_report_analysis` 两表结果推送，值为"低风险"或"高风险"
- `audit_status` / `audited_by` / `audited_at`：人工审查环节，管理员在前端点击"完成审查"时写入

#### 3.4 `contract_analysis` — 前后项合同对比分析

由 LLM 获取 `contracts` 表中同项目的前后项合同，对比分析后写入。**每个项目只有一条记录**，重新分析时 UPDATE 覆盖。

| 字段        | 类型          | 约束                       | 说明                                              |
| :---------- | :------------ | :------------------------- | :------------------------------------------------ |
| id          | UUID          | PK                         | DEFAULT gen_random_uuid()                         |
| contract_no | VARCHAR(100)  | FK → projects(contract_no), UNIQUE | 所属项目（1:1，UNIQUE 保障覆盖式更新）     |
| rate        | DECIMAL(6,4)  |                            | 毛利率：(前项金额 - 后项金额) / 前项金额          |
| rate_level  | VARCHAR(20)   | CHECK IN (正常,低毛利,利润倒挂) | 毛利率等级：正常 / 低毛利 / 利润倒挂         |
| similarity  | VARCHAR(20)   | CHECK IN (完全一致,有一致性风险,完全不一致) | 前后项一致性                       |
| analysis    | TEXT          |                            | Agent 对前后项一致性的详细分析文本                |
| verified    | BOOLEAN       | DEFAULT false              | 是否人工确认                                      |
| verified_by | VARCHAR(50)   |                            | 确认人（用户名快照，非外键）                      |
| verified_at | TIMESTAMPTZ   |                            | 确认时间                                          |
| created_at  | TIMESTAMPTZ   | DEFAULT now()              |                                                   |
| updated_at  | TIMESTAMPTZ   | DEFAULT now()              |                                                   |

**约束与索引**：

```sql
CREATE UNIQUE INDEX idx_contract_analysis_no ON contract_analysis(contract_no);  -- UNIQUE：1:1 保障
ALTER TABLE contract_analysis ADD CONSTRAINT ck_ca_rate_level CHECK (rate_level IN ('正常', '低毛利', '利润倒挂'));
ALTER TABLE contract_analysis ADD CONSTRAINT ck_ca_similarity CHECK (similarity IN ('完全一致', '有一致性风险', '完全不一致'));
```

> `contract_no` 的 UNIQUE 约束让"每个项目一条记录"在数据库层成立，UPSERT 的 `ON CONFLICT (contract_no) DO UPDATE` 有明确冲突列。

**说明**：

- `rate` 判定规则：`< 0` 利润倒挂，`0 ≤ rate < 0.05` 低毛利，`≥ 0.05` 正常
- `similarity` 取值：`完全一致`（条款无差异）、`有一致性风险`（部分条款存在差异）、`完全不一致`（关键条款严重偏离）
- `analysis` 为 LLM 生成的自然语言分析文本，描述前后项合同条款的具体差异和风险点
- `verified`：LLM 分析结果可能出错（如毛利率算反、一致性判断有误），需人工确认后才用于项目风险判定
- 覆盖式更新：重新分析时直接 UPDATE 该记录，`updated_at` 自动刷新，`verified` 重置为 `false`

#### 3.5 `acceptance_report_analysis` — 前后项验收报告对比分析

由 LLM 获取 `acceptance_reports` 表中同项目的前后项验收报告，对比分析后写入。**每个项目只有一条记录**，重新分析时 UPDATE 覆盖。

| 字段        | 类型         | 约束                       | 说明                                              |
| :---------- | :----------- | :------------------------- | :------------------------------------------------ |
| id          | UUID         | PK                         | DEFAULT gen_random_uuid()                         |
| contract_no | VARCHAR(100) | FK → projects(contract_no), UNIQUE | 所属项目（1:1，UNIQUE 保障覆盖式更新）     |

### 七、LLM 分析流程

#### 触发条件

当 `projects` 表中以下四个布尔字段**同时为 `true`** 时，项目**具备 LLM 分析条件**：

```
has_front_contract = true
has_back_contract = true
has_front_acceptance = true
has_back_acceptance = true
```

> **触发方式**：分析由用户在 Agent 对话中**明确指令触发**（如"进行项目风险分析""分析一下这个项目"），**不自动执行**。Agent 检查全部项目，对满足上述条件且 `llm_analyzed = false` 的项目逐个分析。详见 `08.工作流程描述.md` 阶段四。

#### 分析步骤

```
1. 获取 contracts 表中该 contract_no 的前项、后项合同数据
       │
       ▼
2. LLM 对比前后项合同条款
   ├── 计算毛利率：(前项金额 - 后项金额) / 前项金额
   ├── 判定毛利率等级：<0 利润倒挂 / <5% 低毛利 / >=5% 正常
   ├── 分析条款一致性：完全一致 / 有一致性风险 / 完全不一致
   └── 生成分析文本
       │
       ▼
3. 写入 contract_analysis 表（覆盖式 UPDATE：rate, rate_level, similarity, analysis, verified=false）
       │
       ▼
4. 获取 acceptance_reports 表中该 contract_no 的前项、后项验收报告
       │
       ▼
5. LLM 对比前后项验收报告
   ├── 分析内容一致性：完全一致 / 有一致性风险 / 完全不一致
   └── 生成分析文本
       │
       ▼
6. 写入 acceptance_report_analysis 表（覆盖式 UPDATE：similarity, analysis, verified=false）
       │
       ▼
7. LLM 综合两个分析表结果，判定项目风险
   ├── 低风险：毛利率正常 + 两项一致性均无风险
   └── 高风险：利润倒挂 / 低毛利 / 任一一致性为"完全不一致"
       │
       ▼
8. 回写 projects 表：project_risk = 低风险/高风险, llm_analyzed = true
```

#### 毛利率判定规则

| 条件                  | 等级     |
| :-------------------- | :------- |
| rate < 0              | 利润倒挂 |
| 0 ≤ rate < 0.05       | 低毛利   |
| rate ≥ 0.05           | 正常     |

#### 项目风险判定规则

| 条件                                                                           | 风险等级 |
| :----------------------------------------------------------------------------- | :------- |
| 利润倒挂                                                                       | 高风险   |
| 低毛利                                                                         | 高风险   |
| 任一 similarity 为"完全不一致"                                                 | 高风险   |
| 以上条件均不满足                                                               | 低风险   |

> **注**：项目风险判定基于 LLM 分析结果自动生成，但分析表中的 `verified` 字段用于人工确认。管理员可在前端查看分析结果后确认或驳回，确认后分析结果方可用于最终的风险报告。

### 一、概述

本系统由三层构成，端到端业务流程贯穿其中：

| 层级 | 组件 | 职责 |
|:---|:---|:---|
| 感知与分析层 | 本地 Agent（技能） | 文档接收、命名校验、查重、MinIO 上传、LLM 提取、数据推送、LLM 对比分析、综合风险判定 |
| 存储层 | Server（FastAPI + PostgreSQL） | 数据存储、材料完整性标记维护（`has_*`）、API 服务 |
| 展示层 | Frontend（Vue3 + Element Plus） | 卡片展示、人工确认、分析结果查看、项目审查管理 |

### 二、流程总览

```
阶段一 文件准备（用户）
    │
    ▼
阶段二 文档提交（Agent 自动）── 流程A 合同 / 流程B 验收报告
    │   读取→命名校验→类型判断→归档→查重→LLM 提取→推送→维护 has_*
    ▼
阶段三 前端人工确认（审查人员）── 合同/验收 verified
    │
    ▼
阶段四 项目风险分析（Agent + LLM，用户指令触发）
    │   四布尔检查→获取数据→合同分析→验收分析→综合风险→回写 projects
    ▼
阶段五 项目审查与报表（审查人员）── audit_status 完成 + 四报表
```

### 阶段一：文件准备（用户操作）

用户收集一个工程项目的四类文件：

```
① 前项合同.pdf  +  前项验收报告.pdf  （业主与施工方签的原始合同）
② 后项合同.pdf  +  后项验收报告.pdf  （施工方与实际分包方签的分包合同）
```

- 一个项目最多 4 份文件，**前项和后项合同/验收共享同一个合同编号（contract_no）**
- Agent 通过提取合同编号自动判断哪些文件属于同一项目
- 文件格式：PDF 扫描件、PDF 电子版、docx、xls、图片

### 阶段二：文档提交（Agent 自动）

#### 2.1 总体流程

```
用户提交文件（合同 / 验收报告）
    │
    ▼
Step 1. 读取分析文档内容
    │
    ▼
Step 2. 校验文件名规范
   规范格式：项目名称-合同编号-上传人员.扩展名
   ├── 规范 → 直接使用
   └── 不规范 → Agent 生成规范名称，询问用户确认
    │
    ▼
Step 3. 判断文档类型
   ├── 无法判断 → 询问用户"这是合同还是验收报告？"
   ├── 合同 → 走流程 A
   └── 验收报告 → 走流程 B
    │
    ▼
Step 4. 归档文件
   使用规范文件名上传 MinIO，获取 object_key
```

#### 2.2 流程 A：合同提交

```
Step A1. 查重
   调用 GET /api/v1/contracts/check?contract_no=XXX&contract_type=前项
   判断 contract_no + contract_type 是否已存在
   ├── 已存在 → 提示用户"该合同已存在，contract_no=XXX，contract_type=前项"，终止流程
   └── 不存在 → 继续

Step A2. LLM 结构化提取
   发送合同文档给 LLM，按 contracts + projects 表字段提取 JSON
   ├── 提取成功 → 解析 JSON，继续
   └── 提取失败 → 提示用户"文档内容无法识别"，终止流程

Step A3. 推送到服务器
   ├── 查 projects 表是否存在该 contract_no
   │   ├── 不存在 → POST /api/v1/projects 创建项目记录
   │   │             字段：contract_no, project_name, city, responsible_person
   │   │             响应：{"code":0,"data":{"contract_no":"XXX"}}
   │   └── 存在 → 跳过
   │
   └── POST /api/v1/contracts 推送合同数据
       字段：所有提取的合同字段 + source_file_name
       响应：{"code":0,"data":{"id":"uuid","contract_no":"XXX"}}
       │
       后端自动处理：
       ├── 写入 contracts 表
       └── 更新 projects 表对应的布尔标记
           ├── contract_type="前项" → has_front_contract = true
           └── contract_type="后项" → has_back_contract = true

Step A4. 反馈给用户
   "合同已提交：项目 [项目名称]，合同编号 [contract_no]，[contract_type]"
```

#### 2.3 流程 B：验收报告提交

```
Step B1. 查重
   调用 GET /api/v1/acceptance/check?contract_no=XXX&acceptance_type=前项
   判断 contract_no + acceptance_type 是否已有记录
   ├── 已有记录 → 提示用户"该验收报告已存在"，终止流程
   └── 无记录 → 继续

Step B2. LLM 结构化提取
   发送验收报告文档给 LLM，按 acceptance_reports 表字段提取 JSON
   ├── 提取成功 → 解析 JSON，继续
   └── 提取失败 → 提示用户"文档内容无法识别"，终止流程

Step B3. 推送到服务器
   POST /api/v1/acceptance 推送验收报告
   字段：所有提取的字段 + source_file_name
   响应：{"code":0,"data":{"acceptance_id":"uuid"}}
   │
   后端自动处理：
   ├── 写入 acceptance_reports 表
   └── 更新 projects 表对应的布尔标记
       ├── acceptance_type="前项" → has_front_acceptance = true
       └── acceptance_type="后项" → has_back_acceptance = true

Step B4. 反馈给用户
   "验收报告已提交：项目 [contract_no]，[acceptance_type]"
```

#### 2.4 文件命名规范

**格式**：`项目名称-合同编号-上传人员.扩展名`

| 组成部分 | 来源 | 规则 | 示例 |
|:---|:---|:---|:---|
| 项目名称 | 文档内容识别 | 保留原始项目全称 | 黑龙江省（伊春）传输管线工程施工服务项目 |
| 合同编号 | 文档内容识别 | 提取正式的合同号 | XYJAEXJCI250500016 |
| 上传人员 | 用户指定或默认登录用户 | 用户对话中指定，未指定则取当前登录用户名 | 张三 / admin |
| 扩展名 | 保留原始格式 | .pdf / .jpg / .docx | .pdf |

**命名处理步骤**：

```
1. 读取原始文件名
2. 正则匹配是否已符合 "项目名称-合同编号-上传人员.扩展名" 格式
   ├── 匹配 → 直接使用
   └── 不匹配 →
       ├── 从文档内容提取项目名称、合同编号
       ├── 询问用户："请指定上传人员（不指定则默认 [登录用户]）"
       │   ├── 用户输入 → 使用用户输入
       │   └── 用户不输入 → 使用登录用户名
       └── 生成规范文件名 →
           "黑龙江省（伊春）传输管线工程施工服务项目-XYJAEXJCI250500016-张三.pdf"
           并询问用户确认
```

#### 2.5 文档类型判断

Agent 通过文档内容判断类型，判断策略：

| 文档内容特征 | 判断结果 |
|:---|:---|
| 包含"合同"、"甲方"、"乙方"、"签约"、"总金额"等关键词 | 合同 |
| 包含"验收报告"、"验收日期"、"验收结果"、"验收结论"等关键词 | 验收报告 |
| 两者特征都不明显 | 询问用户 |

**交互示例**：
```
用户提交了一个没有明显标识的文档
Agent：我无法在文档中明确判断这是合同还是验收报告，请您确认：
       1. 合同
       2. 验收报告
用户：合同
Agent：好的，按合同流程处理。
```

### 阶段三：前端人工确认（审查人员操作）

审查人员登录 Web 系统，对 Agent 提取的合同/验收报告字段进行核对确认。

```
┌─────────────────────────────────────────────┐
│  合同管理  │  待确认(3)  │ 已确认(15)        │
├─────────────────────────────────────────────┤
│  合同编号            │  类型  │  金额  │  状态    │
│  XYJAEXJCI250500016 │  前项  │ 528万  │  待确认  │  [确认] [编辑]
│  XYJAEXJCI250500016 │  后项  │ 498万  │  待确认  │  [确认] [编辑]
└─────────────────────────────────────────────┘
```

- 核对 LLM 提取的字段是否准确（金额、签约方、条款等）
- 如发现提取错误，点击编辑修正
- 修正后点击确认，设置 `verified=true`
- 确认后不可直接编辑，需取消确认后才可修改

> 人工确认是 LLM 分析结果生效的前置条件之一（阶段四的分析结果也需人工确认，见阶段四）。

### 阶段四：项目风险分析（Agent + LLM，用户指令触发）

#### 4.1 触发方式

用户在对话中发出明确指令，例如：
- "进行项目风险分析"
- "分析一下这个项目的风险"
- "跑一下风险分析"
- "帮我看看有哪些项目需要分析"

> **不自动触发**。即使项目材料齐全，也需用户明确指令才执行分析。

#### 4.2 分析流程

```
用户发出风险分析指令
    │
    ▼
Step 1. 获取全部项目列表
   GET /api/v1/projects
   响应：所有项目记录列表
    │
    ▼
Step 2. 逐项目检查触发条件
   筛选条件：
   has_front_contract   = true
   has_back_contract    = true
   has_front_acceptance = true
   has_back_acceptance  = true
   llm_analyzed         = false

   结果：
   ├── 无项目满足 → 反馈用户 "没有可分析的项目"
   │   ├── 部分材料不齐 → 列出每个项目缺少的材料
   │   └── 都已分析过 → 列出已分析的项目
   │
   └── 有满足条件的项目 → 逐个处理，反馈进度
    │
    ▼
Step 3. 获取前后项合同数据
   GET /api/v1/contracts?contract_no=XXX
   过滤出 contract_type="前项" 和 contract_type="后项" 的两条记录
   │
   同时获取前后项验收报告
   GET /api/v1/acceptance?contract_no=XXX
   过滤出 acceptance_type="前项" 和 acceptance_type="后项" 的两条记录
    │
    ▼
Step 4. LLM 合同对比分析
   ├── 输入：前项合同 JSON + 后项合同 JSON
   ├── 计算毛利率：(前项金额 - 后项金额) / 前项金额
   ├── 判定毛利率等级：
   │   ├── rate < 0          → 利润倒挂
   │   ├── 0 ≤ rate < 0.05   → 低毛利
   │   └── rate ≥ 0.05       → 正常
   ├── 分析条款一致性：
   │   ├── 完全一致（条款无差异）
   │   ├── 有一致性风险（部分条款存在差异）
   │   └── 完全不一致（关键条款严重偏离）
   └── 生成分析文本（自然语言描述差异和风险点）
       │
       ▼
   推送 contract_analysis 表（UPSERT）
   POST /api/v1/contract-analysis
   字段：contract_no, rate, rate_level, similarity, analysis
   （若已存在同 contract_no 的记录则 UPDATE，verified 重置为 false）
    │
    ▼
Step 5. LLM 验收报告对比分析
   ├── 输入：前项验收报告 JSON + 后项验收报告 JSON
   ├── 分析内容一致性：
   │   ├── 完全一致
   │   ├── 有一致性风险
   │   └── 完全不一致
   └── 生成分析文本
       │
       ▼
   推送 acceptance_report_analysis 表（UPSERT）
   POST /api/v1/acceptance-analysis
   字段：contract_no, similarity, analysis
   （若已存在同 contract_no 的记录则 UPDATE，verified 重置为 false）
    │
    ▼
Step 6. LLM 综合判定项目风险
   规则：
   ├── 高风险：利润倒挂 / 低毛利 / 任一 similarity = "完全不一致"
   └── 低风险：以上条件均不满足
       │
       ▼
   PUT /api/v1/projects/{contract_no}
   字段：project_risk = 低风险/高风险, llm_analyzed = true
    │
    ▼
Step 7. 向用户反馈分析结果
   "项目 [contract_no] 风险分析完成：
    - 毛利率：10.00%（正常）
    - 合同条款一致性：完全一致
    - 验收报告一致性：完全一致
    - 综合风险：低风险"
```

#### 4.3 毛利率判定规则

| 条件                  | 等级     |
|:--------------------|:-------|
| rate < 0            | 利润倒挂 |
| 0 ≤ rate < 0.05     | 低毛利   |
| rate ≥ 0.05         | 正常     |

#### 4.4 项目风险判定规则

| 条件                                  | 风险等级 |
|:--------------------------------------|:-------|
| 利润倒挂                               | 高风险   |
| 低毛利                                 | 高风险   |
| 任一 similarity 为"完全不一致"          | 高风险   |
| 以上条件均不满足                        | 低风险   |

> **注**：项目风险判定基于 LLM 分析结果自动生成，但分析表中的 `verified` 字段用于人工确认。管理员可在前端查看分析结果后确认或驳回，确认后分析结果方可用于最终的风险报告。

#### 4.5 重新分析

当用户对已有分析结果不满意时，支持手动重新触发分析：

```
用户：重新分析一下 XYJAEXJCI250500016 这个项目
    │
Agent：好的，我将重置该项目的分析状态并重新分析。
    │
    ▼
PUT /api/v1/projects/XYJAEXJCI250500016
Body: {"llm_analyzed": false}
    │
    ▼
重新执行 Step 3 ~ Step 7
├── contract_analysis 表：UPDATE，verified 重置为 false
├── acceptance_report_analysis 表：UPDATE，verified 重置为 false
└── projects 表：llm_analyzed = true, project_risk 重新推送
    │
    ▼
Agent：重新分析完成，结果如下：
       ...
```

**用户也可以分析指定项目**：
```
用户：分析一下 XYJAEXJCI250500016 这个项目
Agent：好的，我来检查这个项目是否满足分析条件...
       （如果 llm_analyzed=true）该项目之前已分析过，是否要重新分析？
       （如果 llm_analyzed=false 但材料不齐）该项目缺少 [后项合同]，暂无法分析。
```

### 阶段五：项目审查与报表（审查人员操作）

#### 5.1 项目审查

管理员在前端项目详情页查看 LLM 分析结果，确认无误后点击"完成审查"：

```
PUT /api/v1/projects/{contract_no}
Body: { "audit_status": "已完成", "audited_by": "管理员张三" }
```

- `audit_status` 由"待审查"变为"已完成"
- 写入 `audited_by`、`audited_at`

#### 5.2 四个核心报表

```
报表中心
├── 合同内容一致性
│   汇总：各城市 完全一致/有一致性风险/完全不一致 数量
│   明细：每个项目的合同一致性 + 分析文本
│   数据源：contract_analysis
│
├── 验收报告一致性
│   汇总：各城市 完全一致/有一致性风险/完全不一致 数量
│   明细：每个项目的验收一致性 + 分析文本
│   数据源：acceptance_report_analysis
│
├── 低毛利项目
│   汇总：各城市 低毛利/利润倒挂数量
│   明细：合同编号、毛利率、前后金额、等级
│   数据源：contract_analysis (rate_level IN 低毛利/利润倒挂)
│
└── 高风险项目
    汇总：高风险项目数量
    明细：完整项目信息（毛利率 + 合同一致性 + 验收一致性 + 风险）
    数据源：projects (project_risk='高风险')
```

所有报表支持导出 Excel。

### 关键决策点

整个流程中需要人工介入的环节：

| 环节 | 触发条件 | 操作人 | 不处理的后果 |
|:---|:---|:---|:---|
| 文件命名确认 | 文件名不规范 | 用户 | 无法规范归档 |
| 文档类型确认 | 无法自动判断类型 | 用户 | 走错处理流程 |
| 合同/验收信息确认 | 状态=待确认 | 管理员 | 字段未核对，分析基于错误数据 |
| LLM 分析结果确认 | 分析结果 verified=false | 管理员 | 分析结果未生效，不用于最终风险报告 |
| 项目审查完成 | audit_status=待审查 | 管理员 | 项目未闭环，报表口径不完整 |
| 重新分析 | 对分析结果不满意 | 用户 | 维持旧（错误）分析结果 |

### 附录 E：边界情况

| 场景 | 处理方式 |
|:---|:---|
| 用户同时提交多个文件 | 逐个文件串行处理，每个文件独立完成完整流程后再处理下一个 |
| 用户提交的文件不是合同也不是验收报告（如发票、资质证书） | 提示用户不支持该类型文档，询问是否有需要处理的合同/验收报告 |
| 用户提交的合同没有明确的 contract_no | LLM 尝试提取，无结果则询问用户手动输入 |
| 用户提交的合同没有明确的 contract_type | LLM 根据转包关系判定，若无法判定则询问用户 |
| 同一个文件被重复提交两次 | 第一步查重即拦截，提示已存在 |
| 风险分析时部分项目材料不齐 | 完成可分析的项目，汇总时告知哪些项目因缺少材料被跳过 |
| 用户要求分析的项目不存在 | 提示"该项目不存在，请确认合同编号是否正确" |
| LLM 提取的金额格式不标准 | 要求 LLM 输出纯数字，Agent 做一次正则清理（去逗号、去单位） |
| 前项金额为 0 导致毛利率除零 | rate 标记为 null，rate_level 标记为"无效"，不计入风险判定 |

### 一句话总结

> **用户把合同/验收文件丢给本地 Agent → Agent 自动命名、上传、提取、入库（维护材料完整性标记）→ 审查人员在网页确认提取结果 → 用户下达分析指令后 Agent 用 LLM 对比前后项合同与验收、计算毛利率、综合判定项目风险 → 审查人员确认分析结果、完成审查 → 生成四个维度的统计报表。**

整个过程从原始 PDF 到最终的风险报表，经过两次人工核对（提取确认 + 分析确认）与一次审查闭环。

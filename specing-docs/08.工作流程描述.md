### 阶段一：文件准备（用户操作）

```
用户收集一个工程项目的两类文件：
  ① 前项合同.pdf  +  前项验收报告.pdf  （业主与施工方签的原始合同）
  ② 后项合同.pdf  +  后项验收报告.pdf  （施工方与实际分包方签的分包合同）
                   │
                   ▼
        按合同编号整理文件，例如：
        HT-2024-001_XX市住建局/
          ├── 前项_HT-2024-001_XX建设工程.pdf
          ├── 后项_HT-2024-001_XX建设分包.pdf
          ├── 前项验收_HT-2024-001.pdf
          └── 后项验收_HT-2024-001.pdf
```

- 一个项目有 2~4 份文件，**前项和后项合同共享同一个合同编号（contract_no）**
- Agent 通过提取合同编号自动判断哪些合同属于同一项目，并完成前后项配对
- 文件命名中的"前项/后项"是辅助信号，非必需
- 文件格式：PDF 扫描件、PDF 电子版、docx、xls、图片
- 批量处理时，入口就是一个包含多个项目目录的根文件夹

### 阶段二：本地 Agent 处理（自动化）

用户在本地运行 Agent 脚本，传入文件目录：

```
python agent/batch_process.py --dir ./projects/2025年项目/
```

**步骤 2.1：文件类型判断**

```
        文件
          │
    ┌─────┴─────┐
    │           │
 PDF扫描件     PDF有文本层 / docx / xls
    │           │
  PaddleOCR    直接提取文本
    │           │
    └─────┬─────┘
          │
      OCR 原始文本
```

- 扫描件/图片 → PaddleOCR 识别 → 输出文本
- 电子版 PDF/docx → 直接提取文本
- xls/xlsx → 提取表格数据

**步骤 2.2：LLM 结构化提取**

将 OCR 文本发给大模型，按合同模板提取字段：

```
输入：OCR 原始文本（约 1k~10k 字）

输出：结构化 JSON
{
  "contract_no": "HT-2024-001",
  "party_a": "XX市住建局",
  "party_b": "XX建设工程有限公司",
  "total_amount": 5280000.00,
  "signing_date": "2024-03-15",
  "payment_terms": "...验收合格后30日内支付至95%...",
  "acceptance_terms": "...竣工后15日内组织验收...",
  "breach_terms": "...每延误一日按合同价0.05%支付违约金...",
  "line_items": [
    {"item_no": 1, "item_name": "土建工程", "unit": "项", "quantity": 1, "unit_price": 2000000, "amount": 2000000},
    {"item_no": 2, "item_name": "设备采购", "unit": "套", "quantity": 5, "unit_price": 300000, "amount": 1500000}
  ]
}
```

**步骤 2.3：前后项判定**

Agent 通过合同编号自动匹配同一项目的前后项合同。判定优先级：

```
① 合同编号匹配 → 如果两个合同有相同的 contract_no，它们属于同一项目
② 文件名信号 → 含 "前项" / "后项" / "上家" / "下家" 辅助判定
③ 签约方比对 → 甲方=业主的一般是前项，乙方=分包方的是后项
④ 仍无法判定 → 标记"待人工指定"，前端确认
```

核心逻辑：Agent 提取 `contract_no` 后，在服务端查询是否已有相同 `contract_no` 的记录。若有，则新合同与已有合同配对；若无，则创建新的项目记录。

**步骤 2.4：推送到服务端**

```
POST /api/v1/contracts
{
  "contract_no": "HT-2024-001",
  "contract_type": "前项",
  "party_a": "XX市住建局",
  "party_b": "XX建设工程有限公司",
  "total_amount": 5280000.00,
  "ocr_raw_text": "...",
  "source_file_hash": "sha256:xxxx",
  ...
}

      ↓

服务端：
 ① 查询 projects: contract_no 是否存在？
    - 否 → INSERT INTO projects (自动创建项目)
 ② INSERT INTO contracts
 ③ INSERT INTO line_items
 ④ 返回 contract_id

Agent 记录 contract_id，继续处理下一个文件
```

- 自动配对：当同一 `contract_no` 的两份合同（前项+后项）都入库后，系统标记"可配对"
- 断点续跑：已经处理的文件会跳过（通过 file_hash 去重）

### 阶段四：比对引擎执行（服务端自动）

**步骤 4.1：数值比对（纯计算，毫秒级）**

取出前项和后项的分项清单，逐项匹配：

```
前项：
  土建工程  1项 × 200万 = 200万
  设备采购  5套 × 30万  = 150万
  合计：528万

后项：
  土建工程  1项 × 185万 = 185万
  设备采购  5套 × 28万  = 140万
  合计：498万

比对结果：
  ┌─────────────┬────────┬────────┬───────┐
  │ 分项        │ 前项    │ 后项    │ 差异   │
  ├─────────────┼────────┼────────┼───────┤
  │ 土建工程     │ 200万  │ 185万  │ -15万  │
  │ 设备采购     │ 150万  │ 140万  │ -10万  │
  │ 合计         │ 528万  │ 498万  │ -30万  │
  │ 毛利率       │  —     │  —     │ 5.68%  │
  └─────────────┴────────┴────────┴───────┘

  ＞ 毛利率 = (528 - 498) / 528 ≈ 5.68%
  ＞ 大于 3%，不算低毛利

分项匹配规则：
  "土建工程" vs "土建工程" → 名称相似度 > 80%，精确匹配
  匹配后计算数量/单价/金额差异、单项毛利率
```

**步骤 4.2：LLM 语义比对（异步，秒级）**

对关键条款做逐项比对：

```
付款条款比对：
  前项：".。。验收合格后30日内支付至95%，质保期满后支付剩余5%。。。"
  后项：".。。验收合格后60日内支付至90%，余款10%在质保期满后支付。。。"

  → LLM 判定：不一致
  → 差异详情：付款节点相差30天，付款比例前后差5%

交付条款比对：
  → 一致

验收条款比对：
  → 一致

↓↓↓

INSERT INTO comparisons
  (amount_match='一致', payment_match='不一致',
   payment_diff_detail='付款节点：前项"验收后30日内"，后项"验收后60日内"，差30天；'
                       '付款比例：前项95%，后项90%，差5个百分点',
   ...)
```

**步骤 4.3：自动风险判定**

比对完成后，自动写入风险记录：

```
规则引擎逐条判定：

① 毛利率 < 0%？  → risk_type='利润倒挂', risk_level='高'
② 毛利率 0~3%？  → risk_type='低毛利', risk_level='高'
③ 毛利率 3~5%？  → risk_type='低毛利', risk_level='中'
④ 后项数量 > 前项 110%？  → risk_type='超量分包', risk_level='中'
⑤ 后项单价 > 前项单价？  → risk_type='单价倒挂', risk_level='高'
⑥ 任意条款不一致？  → risk_type='条款不一致', risk_level='中'
⑦ 验收内容不一致？  → risk_type='验收不一致'
⑧ 验收日期异常（后项日期在前项之前）？  → 标记异常

↓↓↓

INSERT INTO risk_records
  (risk_type='低毛利', risk_level='中',
   source_type='comparison', source_id='...',
   detail='毛利率5.68%，正常范围')
```

### 阶段五：验收报告处理（独立流程）

验收报告的处理与合同流程平行，逻辑相同：

```
Agent 处理验收文件 → POST /api/v1/acceptance → 前端人工确认 → 触发比对

比对内容：
  · 验收内容一致性（LLM 判断 "通过" 的内容是否一致）
  · 验收日期逻辑（前项验收日期应早于或等于后项验收日期）
  · 验收结果（通过/不通过/附条件通过）

比对结果 → 写入 acceptance_reports.comparison_result

同时触发风险判定：
  · 验收内容不一致 → risk_type='验收不一致'
  · 日期逻辑异常（后项先验收、前项未验收） → 标记异常
```

### 关键决策点

整个流程中有几个地方需要人工介入：

| 环节 | 触发条件 | 操作人 | 不处理的后果 |
|:---|:---|:---|:---|
| 合同信息确认 | 状态=待确认 | 管理员 | 无法参与比对 |
| 前后项修正 | 自动判定错误 | 管理员 | 比对配对错误 |
| 风险忽略 | 误报 | 管理员 | 报表数据不准确 |
| 合同字段纠正 | LLM 提取有误 | 管理员 | 比对结果偏差 |

---

### 一句话总结

> **用户把合同文件丢给本地 Agent → Agent 自动 OCR + 提取 + 入库 → 审查人员在网页上点几下确认 → 系统自动比对金额和条款、计算毛利率、标记所有风险 → 最终生成四个维度的统计报表。**

整个过程从一份原始 PDF 到最终的风险报表，只经过了一次人工核对环节。
